# Inky Paper：P0—P1 迭代推进计划

**计划日期：2026-09-16**  
**分析基线：Inky Paper 0.6.4，提交 `d13b19f7ddf518b7c83a5a3627f852ba4cbda0a9`。**  
**状态：待实施。本文是推进计划，不代表功能已经实现、测试已通过或代码已提交。**  
**范围：完成上一轮分析中的全部 P0 和 P1；不纳入 P2。**

## 1. 本轮目标与边界

把现有应用完善为一条可反复使用的流程：

**工作台安排和调整 → Paper 开始与执行 → 低成本留下反馈 → Coach 基于记录给建议 → 用户确认下一次安排。**

| 部分 | 本轮职责 | 不承担的职责 |
| --- | --- | --- |
| 工作台 | 全局任务、今日计划、遗留事项、时间安排、项目背景、记录与 Coach 对话 | 不替用户启动或结束专注 |
| Paper | 当前步骤、今日执行队列、计时、快速记录与轻量收尾 | 不复制完整项目管理与复杂日历界面 |
| Coach | 按需交流、规划、调整和总结；提出可核对的候选 | 不自动介入、不代替用户采用计划、不把计时解释为注意力 |
| 共同数据层 | 统一对象、版本化操作、执行事实、可追溯导出 | 不建立第二套任务数据库，不用 Markdown 反向覆盖任务 |

### 1.1 复用现有能力，不重复建设

基线已包含独立工作台、三日计划与日程、跨日拖动、每日记录与 Markdown、Coach 对话历史/续聊/取消、可编辑采用卡片、返回 Inky 并准备步骤、结束反馈与执行回流。[R1][R2]

本轮是在这些能力上补齐规则和体验，不重做工作台、聊天窗口、番茄钟或 Markdown 同步。

### 1.2 不变的产品和数据规则

1. 保留 Inky Paper 的简洁纸面风格、独立专注页、透明宠物；不加入等级或养成体系。
2. `Do this`／“设为下一步并回到 Inky”只准备步骤；`start` 才开始计时。回到列表、打开工作台不应改变当前计时。
3. 步骤完成与父任务完成独立；只能由用户显式确认完成父任务。
4. 开始执行后保留步骤与会话快照；后续改名、改期、重排不改写既往执行事实。
5. SQLite 是任务和执行事实源。生成 Markdown 是导出；用户个人笔记独立保留，外部编辑不能被覆盖。
6. 继续使用命名事务、对象版本和请求标识；不新增全量状态覆盖接口。重试同一操作复用同一请求标识及完全相同参数。
7. Coach 仅在用户发送请求时调用；时间到点、任务变化、记录保存不触发模型。保留已有普通到点提示。
8. 计时、自报精力、产出和完成状态分开处理；未报告保持未知，不诊断、不打生产力分数。
9. 日期以应用当前时区和请求中明确的日期为准；区分“真实今天”“查看日期”“本次回复日期”，不能只按聊天记忆推断。
10. 开发和桌面验证使用独立测试数据，不使用旧版 Inky-app 数据，不修改其他 Hermes/MCP 连接。

上述基础边界来自现有实现约定与 Coach 规则，本轮继续沿用。[R3][R4]

### 1.3 明确不做

第三方日历同步、复杂自动排程、后台自动 Coach、跨工具自动执行、附件上传与整库知识检索、复杂项目依赖图、宠物养成、额外统计大屏，以及工作台内完整模型账户管理。只做连接诊断，不扩展为模型配置中心。

每个阶段合并后保持可运行，版本号在实际交付时决定。不要在一个巨大提交中一次性实现全部 P0/P1。

## 4. M0：对齐基线与共同规则

**目标：先消除会导致两个界面各做一套逻辑的歧义。**

### M0.1 代码与数据基线

核对当前工作目录、分支、未提交改动和已合并内容。分析基线是 0.6.4；开发时若 `main` 已变化，先逐项比对，已完成的需求标记为复用或待验证，不覆盖后续工作。记录本轮实际起始提交。

在独立测试目录重跑现有检查并记录结果。历史文档中的测试通过数字不能算作本轮通过。先准备旧格式数据副本，用于字段迁移、空值兼容和恢复验证。

### M0.2 统一字段语义

| 信息 | 建议归属 | 本轮规则 |
| --- | --- | --- |
| 标题、分类、优先级 | 任务 | 两端共用，不为工作台复制字段 |
| 截止备注 | 任务 | 保留旧自由文本，不自动解析后覆盖 |
| 可选结构化截止日期 | 任务 | 与安排日期独立；旧数据默认空；有歧义需确认 |
| 动作、完成标准 | 步骤 | 简短标题和完成标准分开；不得修改历史快照 |
| 首轮时长 | 步骤/准备执行配置 | 代表一次计时建议，不代表全部工时 |
| 安排日、顺序、开始时刻、预留时长 | 当日安排 | 同一步骤可跨日继续；同日重复采用复用已有安排 |
| 实际计时、产出、卡点、下次起点 | 会话/记录 | 仅来自真实执行或用户明确反馈 |
| 当天可投入时间 | 日约束，M4 | 可不填；不从空白时间推断 |
| 项目背景、用户偏好 | 独立的版本化上下文，M4 | 与任务事实和当天状态分开；按授权范围使用 |

具体类型和存储迁移由实现阶段结合现有架构确定。新增字段默认可空，先兼容读取，再接写入、导出和模型上下文。

### M0.3 统一查询与状态规则

工作台与 Paper 必须使用同一套“今日队列、待安排、遗留事项、完成状态”的定义；可以共享纯函数或后端查询，但不允许两个页面分别维护相似过滤逻辑。

当前队列可以显示步骤最新状态；历史回顾按当时记录和事件解释，不能把之后的撤销改写为过去从未完成。计划修改也要保留来源日期和变更事件，避免复盘时把修改后的计划当成当时原计划。

### M0.4 交付与验收

建议形成公共约定、需求台账和验收用例三个文档；路径由仓库现有文档结构决定。每个工作包包含负责人、状态、相关提交和验收证据。

**放行：** 字段含义、继续/改期/取消安排的差异、当前会话保护、模型写权限、迁移方式已清楚；两个执行任务以同一份约定开始。

## 5. M1：统一今日安排与 Paper 执行（P0）

### M1.1 遗留未完成处理：W-01

增加可折叠的“待处理的旧安排”。以任务/步骤标识归并，不因为一个步骤在多个过去日期安排过，就显示多个重复待办。

- **今天继续：** 使用原 taskId/stepId 建立或复用今天的安排；保留原有历史，记录旧安排已处理。
- **改期：** 预览目标日期和时刻；只调整安排，不复制父任务，不改变已发生会话。保留计划变更记录。
- **取消本次安排：** 只取消选中的安排；存在其他有效安排时，不能声称该步骤已回到待安排。
- **放回待安排：** 明确列出将取消的未执行安排，经用户确认后处理；保留历史关系与执行记录。

已完成父任务或步骤不进入遗留待办。已安排到未来的未完成步骤明确标记“已重新安排”，默认不反复催促处理。不得自动把所有旧任务塞入今天。

**验收：** 同一步骤跨日仍是同一对象；今天已有安排时不重复新增；改期后历史可追溯；取消部分安排和放回待安排的提示准确。

### M1.2 字段与编辑能力一致：W-02

工作台详情补齐优先级、截止备注、可选截止日期、步骤完成标准。Paper 默认保持精简，需要时展开或引导到工作台，不把全部管理字段放到首页。

新字段接入共同后端操作、读取类型、相关 Markdown 导出及 Coach 读取结果。新增结构化截止日期不替代或强行解析既有备注。

**验收：** 任一端修改后另一端读取相同值；旧数据没有新字段仍正常打开；安排日期和截止日期互不自动修改；完成标准不被标题改动意外清空。

### M1.3 Paper 今日队列：P-01

便签继续表示当前准备执行的步骤。下方默认显示今天安排的步骤并沿用工作台顺序；保留“全部任务”和“临时做一件”的次级入口。

当天刚完成的内容在原位置划线，不能立即消失。无今日计划时可直接添加或从未安排事项开始，不要求先完成每日规划。用户临时执行未来步骤或未安排步骤时，实际发生日与原安排日期分开记录，不能暗中改期。

**验收：** 工作台重排和跨日移动后两端一致；没有今日计划仍可开始；计划外工作进入实际记录；临时执行不会把未来计划伪装为今日原计划。

### M1.4 交接与计时保护：P-02

复用已有“设为下一步并回到 Inky”。展示必要的任务、步骤、本轮时长和进行中状态。当前有未保存会话时，保留已有切换保护，提供返回本轮的入口。

**验收：** 看列表/工作台不暂停或重置计时；外部重排不换掉当前步骤快照；任务和步骤完成独立；所有成功提示都基于确认的后端结果。

### M1 阶段放行

用一组包含昨天未完成、今天安排、未来安排、计划外执行和手动完成的测试数据，完成“处理遗留 → 今天排序 → 返回 Paper → 完成一轮 → 工作台和 Markdown 查看”的原生桌面验收。

## 6. M2：让 Coach 能交流，也能调整已有计划（P0）

### M2.1 请求入口与上下文：C-01

输入区域保留“安排一下 / 我卡住了 / 回顾一下”入口，不仅在空白对话出现。点击可预填问题，只有用户发送后才调用模型。

每次请求保存：明确日期和时区、所选任务/步骤、请求意图、最新相关事实与版本、用户明确的临时约束。按意图读取相关范围，不默认塞入全部历史，也不将聊天记忆当作最新事实。

信息足够时直接建议；只追问会改变结果的缺失内容。对“卡住”优先区分缺信息、依赖未满足、范围过大和用户自报状态；不先让用户填长问卷。

**验收：** 旧会话切换日期/任务后不沿用旧范围；处理中切日仍保留本次请求范围；无自报精力时不补造；简单事项不会强制拆成多个步骤。

### M2.2 计划调整候选：C-02

在现有候选机制上增加以下最小动作集：继续原步骤、调整顺序、改期、修改预留时长、缩小步骤范围。日期、受影响对象标识和变更字段存入结构化候选，不只写在聊天文案里。

对缩小范围尤其要保留原目标：优先新增更小的可执行步骤，或显式展示原步骤的变更；不能通过缩短文字悄悄丢失剩余工作。历史执行仍指向原快照。

采用前展示“哪些保留、哪些改变、改变的原因、目标日期/时刻”。支持选择独立变更；存在依赖的变更作为一个组共同选择。

### M2.3 采用与校验

应用候选前由本地校验：目标对象仍存在、任务和步骤版本、受影响安排/排序状态、所需前置动作、进行中的会话限制。

采用的变更集合在同一事务中完成，失败不得留下半套安排。独立组可分别采用，但每组都有稳定标识。重复点击或响应丢失后重试，不重复创建对象；用户修改候选参数后是新操作，不冒用旧请求标识。

候选的采用命令不暴露给模型。检查既有任务写工具是否可绕过确认；在 Coach 使用路径中阻止未确认的直接计划写入，保留正常用户手动编辑。不得用提示词代替新增写操作所需的权限边界。

**验收：** 未采用不改正式计划；只采用选中项；计划已变时阻止覆盖并保留草稿；不启动时钟、不自动完成任务、不通过重试产生重复任务。

### M2 示例验收

预置当天已有 3 个步骤。用户说“今天只有 60 分钟，先推进最重要的部分”。Coach 应复用原任务/步骤，给出保留、缩小或延期建议；用户采用后工作台和 Paper 显示同一结果，而不是新增一套重复任务。

**P0 完成门槛：M0—M2 全部通过，形成可独立交付的主流程版本。**

## 7. M3：减少添加、记录、收尾和继续的阻力（P1）

### M3.1 工作台操作减负：W-05

快速添加仅要求标题，下一步可默认与标题相同；分类、截止信息、步骤标准等按需补充。不要强迫简单事项经过长表单或 Agent 拆分。

编辑草稿按对象保存并在关闭/重开后恢复；源对象变化时提示冲突而非直接覆盖。批量改期复用 M1/M2 共同操作和预览，不新写一条绕过版本校验的路径。

Coach 侧栏可收起并保留对话与输入草稿。收起不是取消正在进行的请求；需要取消时使用明确操作。

连接诊断区分：本机依赖未找到、Hermes 未连通、Paper 工具不可用、模型调用失败；提供针对性说明和重试。诊断不应展示密钥、令牌或原始活动标题，不要求修改全局配置。

### M3.2 收尾反馈：P-03

保留“产出、卡点、下次起点”三个底层字段，但按用户选择优先显示一个最相关问题。

| 状态 | 优先问题 | 可展开内容 |
| --- | --- | --- |
| 已完成 | 留下了什么？ | 卡点、下次起点 |
| 还没完成 | 下次从哪里开始？ | 已有产出、卡点 |
| 用户明确表示卡住 | 主要卡在哪里？ | 可选原因和自由文本 |

全部可跳过；“还没完成”不等于“没有进展”或“遇到卡点”。保留完成选项与笔记的草稿恢复，保存成功后才提交结果。

### M3.3 继续路径：P-04

未完成时保留起点，用户可继续原步骤；完成后允许挑选下一步或休息，不自动开始下一轮。已有完成反馈和休息选择继续保留，不新增强制中间页。

全部步骤完成时提供轻量确认“整个任务也完成了吗？”用户可选择完成父任务或保留后续。不要根据步骤计数自动完成父任务，也不要反复弹窗。

将同一条下次起点用于 Paper 便签、工作台详情和 Coach 上下文，不重复维护三份文本。

### M3.4 收集与整理：P-05

专注时继续快速随手记，不强迫分类。工作台增加集中处理入口，支持保留为笔记、转换为新任务或关联已有任务。

转换保留原 noteId、原文、来源任务/会话与转换关系；重复点击复用已转换目标，不能生成重复任务。不得因为转换而删除原记录。新增整理状态要兼容旧笔记，并使用共同持久化操作。

### M3 阶段放行

完成“临时想到一件事 → 随手记 → 回到专注 → 不填反馈保存 → 工作台整理笔记 → 下次继续”的真实流程。记录前后点击数和操作耗时，观察是否下降，不以提高强制填写率作为成功标准。

## 8. M4：让规划理解时间、项目与个人偏好（P1）

### M4.1 日投入与冲突检查：W-03

可选维护当天可投入分钟数和明确的不可用时间；未填写时保持未知。保留必要的日期、修改时间和来源，用户可随时修改。

展示已明确的预留总量、未估计项、日程重叠。计划投入按预留时长计算，不把首轮计时当作总工时。未估计项不能算作 0，也不能宣称计划已完全适配。

区分“总计划投入”与“日历占用”：重叠任务本身要提示冲突；不能因为时间区间合并后变短，就把两项工作视为都能完成。

超量或冲突时给“自己调整 / 请 Coach 帮我取舍”的入口；只有用户发送请求才调用。采用调整继续走 M2 的版本化候选机制，不自动延长工作时间。

### M4.2 轻量项目与背景：W-04

工作/学习/生活/想法继续作为分类，不再把分类下拉框冒称为项目。增加独立的可选项目关联，支持创建、改名和归档；旧任务保持原分类，默认无项目。

项目只保留最小信息：名称、当前目标、完成标准、用户填写的参考链接。任务可绑定项目，工作台可筛选项目；Paper 最多展示一个轻量标记，不展开完整项目管理。

项目背景可进入相关 Coach 请求。参考链接仅保存与显式打开，不代表系统已抓取或阅读链接内容；外部全文检索不在本轮范围。

归档项目不删除任务和记录。项目改名不改变执行快照；相关导出和 Coach 读取结果使用同一项目标识。

### M4.3 偏好和背景分层：C-04

| 信息 | 生效范围 | 处理方式 |
| --- | --- | --- |
| 首轮通常偏好 15 分钟 | 长期偏好 | 经用户明确确认后保存，可查看/修改/停用/删除 |
| Inky 目前优先减少执行阻力 | 项目阶段 | 与项目关联，阶段变化可更新 |
| 今天只有 45 分钟 | 当天 | 到期不继续套用，历史仍可追溯 |
| 这次有些累 | 当前请求或明确日期 | 作为自报状态使用，不自动写成长期特征 |

复用 Hermes 已有提供方，不建设第二套完整长期记忆系统。优先由 Inky 管理需要可见、可纠正的结构化偏好，再按需提供给 Coach。

事实冲突时，最新共同数据库优先于聊天旧状态；当前明确要求优先于旧偏好。用户删除 Inky 偏好后应停止在 Inky 请求中使用；如果 Hermes 还保留独立历史，必须说明删除范围，不能假称所有提供方的历史均已删除。

### M4 阶段放行

同一组任务分别在“没有时间约束”“只有 45 分钟”“项目目标改变”“长期偏好被纠正”下测试。建议应反映明确变化，但不得自行推断没有提供的事实。

## 9. M5：总结、评测与完整交付（P1）

### M5.1 有依据的总结：C-03

继续复用现有读取记录和版本化保存总结的流程。正文保持简短，分为：实际推进、与计划的差异、已报告的卡点/仍未知的原因、下次起点。

关键事实关联具体会话、步骤、手动变更或笔记；界面能查看对应依据，必要时显示读取截至时间。不将后续状态覆盖为历史事实，不把手动完成当作计时。

已有记录变化后提示总结已过时；用户再次请求才重读并更新。保存时同时校验数据版本和个人笔记版本；冲突则重读，不静默保存旧总结。

下一次起点提供“继续原步骤”或“生成候选”，采用仍需用户确认。用户明确询问时支持轻量多日回顾，按同样证据规则处理，不新增统计大屏或自动周报。

### M5.2 Coach 质量评测：C-05

建立不少于 24 个固定场景，覆盖交流/规划、已有计划调整、总结与证据三类。关键模型场景每类选择样本重复调用，记录模型/配置、输入事实版本、可见回答、工具行为与评价；真实模型测试仅用隔离测试任务。

必须覆盖：简单事项不强拆、时间不足会取舍、旧建议冲突、半数采用、日期切换、跨日执行、手动完成与撤销、没有产出、自报精力缺失、资料不足、断线重试、模型不得控制时钟。

权限越界、编造已保存、错误日期写入、重复创建、未确认采用、历史事实被改写属于发布阻塞项。固定测试样本中出现一次就修复并重跑；测试通过不等于宣称模型永远不会犯错。

其他质量按“有无必要追问、动作能否开始、是否保留原目标、解释是否简短有据、建议是否适合当前约束”比较迭代前后样本。先建立基线，不预先承诺提升百分比。

### M5.3 使用效果的观察口径

| 目标 | 观察方式 | 注意事项 |
| --- | --- | --- |
| 更容易开始 | 选定事项到开始计时的操作数和耗时 | 与用户正在思考的时间区分，不推断专注质量 |
| 更容易维护计划 | 遗留事项处理、重复安排、改期后可找到的比例/案例 | 未安排不等于失败 |
| Coach 更实用 | 直接采用、修改后采用、拒绝及可选原因 | 拒绝不自动判定模型差，保留情境 |
| 收尾更轻 | 收尾操作耗时和是否能跳过反馈 | 不靠强制填表提高数据量 |
| 总结更可信 | 事实证据对应、未知是否保留、建议能否继续原工作 | 不以文字数量评价质量 |

优先使用隔离验收和用户自愿的本地记录，不新增默认远程遥测。必要的操作元数据与聊天正文、个人笔记、活动标题分开；质量评测材料使用合成或脱敏数据。

### M5.4 技术与原生桌面验证

按仓库实际配置运行并记录输出，基础命令为：[R2][R3]

```powershell
corepack pnpm typecheck
corepack pnpm test:frontend
cargo test --manifest-path src-tauri/Cargo.toml
corepack pnpm tauri build --no-bundle
```

在 Windows 原生 Tauri/WebView2 的独立数据环境验证：双窗口同步、最小工作台宽度与既有纸面尺寸、键盘和输入法、草稿恢复、透明/迷你态、进行中/暂停/到时、结束页与休息、跨午夜、手动完成/撤销、外部个人 Markdown 编辑、断线、重复请求和版本冲突。前端单元测试不能替代真实桌面验收。

新增字段完成旧数据迁移、失败恢复与兼容验证。数据库迁移前保存可恢复的备份；如果升级后产生新数据，回退不能只替换旧 exe，需明确兼容能力和新增数据处理方式。

### M5.5 交付

形成代码提交、需求完成台账、自动测试结果、真实模型样本、桌面验收证据、迁移与恢复说明、更新后的使用说明和项目状态。

由单一集成任务构建交付文件，验证版本、构建提交和 SHA-256，再按既有流程更新 `app/Inky Paper.exe`。不要用任一未集成分支的 exe 代表整轮交付；覆盖用户正在使用的程序前，先正常保存并结束当前工作。

若某项缺少真实桌面或模型证据，标为“已实现、待验收”，不得写“P1 全部完成”。

## 10. Codex 并行分工

仓库已有纸面执行与工作台两个 worktree 的协作约定。本轮沿用职责分离，但开始前核对实际分支和目录，不复用历史绝对路径。[R5]

| 角色 | 主责 | 写入边界 |
| --- | --- | --- |
| A：Paper 执行 | 今日队列、快速收集、收尾、继续路径、Paper 侧字段呈现 | 主要修改 `src/paper/`；不独立重定义共同接口 |
| B：工作台与 Coach | 遗留事项、编辑与日程、候选调整、项目/偏好、对话与总结 | 主要修改 `src/workbench/`、工作台后端、Coach 与 MCP 集成 |
| 集成负责人 | 共同模型、后端事务、迁移、冲突处理、回归、发布 | 公共写入保持单一负责人；可由同一个 Codex 任务分阶段承担，不必第三个长期 Agent |

M0 先合并公共约定。M1 各自改界面时依赖已约定的接口；共享类型、`paper.rs`、`paper_planning.rs`、`main.rs`、版本与锁文件只由明确的负责人修改，其他角色提出局部变更请求。

M2 由 B 主导，A 配合验证执行交接。M3 和 M4 在共同数据约定稳定后并行。M5 集中验收和交付。

每个 worktree 独立端口、应用标识、测试库和 WebView 配置。禁止复制另一目录整份源文件覆盖、共享正式数据库运行验收、擅自清理未提交修改。合并以 Git 提交为单位。

### 每个工作包的完成流程

领取一个编号 → 确认依赖与涉及文件 → 补充验收用例 → 实现最小闭环 → 本地测试 → 提交和交接 → 集成验收 → 更新台账。

状态统一为：**未开始 / 进行中 / 已实现待验收 / 已验收 / 阻塞**。只写“代码已生成”不算完成。

## 11. 完整 P0/P1 验收清单

- [ ] 两端的今日队列、顺序和所选步骤一致。
- [ ] 遗留事项可继续、改期或收回；不会重复生成父任务或同日步骤安排。
- [ ] 优先级、截止备注/日期、完成标准、项目信息在所需界面和读取结果中一致。
- [ ] 旧数据和空字段可用，迁移有备份，历史快照不被修改。
- [ ] Coach 理解明确的日期、任务、意图和约束；无关旧上下文不污染当前建议。
- [ ] 计划调整有结构化对象和差异预览；采用只由用户触发；版本冲突和重复请求正确处理。
- [ ] Paper 可独立执行临时事项；专注页仍独立，迷你态和整体轻量设计保留。
- [ ] 收尾反馈可跳过；已有草稿不丢失；未完成不等于失败，父任务不自动完成。
- [ ] 随手记可集中处理，转换保留来源且不重复生成任务。
- [ ] 快速添加、草稿恢复、批量改期、侧栏收起和连接诊断可用。
- [ ] 时间预算区分未知、待估计、预留和实际；不会将首轮计时当作总工时。
- [ ] 项目可创建、编辑、筛选和归档；旧分类不被项目替代。
- [ ] 偏好可查看与纠正；临时状态不过度长期化；删除范围说明准确。
- [ ] 总结有事实依据和版本，下一步可转候选但不会自动采用。
- [ ] 固定 Coach 案例、真实模型测试、自动测试和原生桌面验证都有本轮证据。
- [ ] 文档、构建与交付记录齐全，用户数据备份和恢复路径可用。
