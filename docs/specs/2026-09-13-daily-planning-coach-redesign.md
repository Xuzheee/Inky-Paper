# Inky Paper：每日计划、执行与 Coach

日期：2026-09-13。状态：已按用户确认进入实现，验收证据见同目录的分步实现记录。以下描述本轮采用的设计；使用效果仍需日常试用检验。

本稿从本次提出的三个目标重新设计：计划与记录保存为 Markdown；Coach 能读取全部任务、计划和记录，结合专业知识提供建议；用户通过 Agent 安排每天的工作，在 Inky Paper 中逐轮执行。已移出的旧方案不作为本稿依据。

日常流程：**用户询问 Coach → 拆分为候选卡片 → 用户选择并加入 Inky → 在 Paper 逐轮执行 → 自动保存执行记录 → 用户询问时生成每日工作总结。**

用户已明确：Coach 不主动介入，只有用户询问时才发起。结束一轮、遇到卡点、长时间未操作、记录更新和收工，都不自动调用 Coach。普通保存、同步和番茄钟到点提示属于应用功能，不需要模型参与。

## 一天怎样使用

| 时机 | 使用者做什么 | 产品怎样接住 |
| --- | --- | --- |
| 准备工作 | 在 Hermes 询问如何安排或拆分待办，必要时补充可用时间 | Coach 先读最新任务和相关记录，再给出可选择的执行卡片 |
| 采用计划 | 调整卡片，勾选想做的事项，点击“加入 Inky” | 只将选中卡片加入指定日期的计划；保存成功后在 Paper 显示，不自动启动番茄钟 |
| 开始一轮 | 在 Paper 选择当前动作和时长，启动番茄钟 | 带入任务与这一步要取得的结果，自动记录开始、暂停与结束 |
| 一轮结束 | 选择继续、完成这一步或遇到卡点，可补一句产出 | 保存实际记录并更新卡片进度；可以继续、休息或换下一张；询问 Coach 才发起求助 |
| 收工与次日 | 查看记录，向 Coach 说“总结今天的工作”或“帮我安排明天” | 读取指定日期的最新计划与执行事实，生成并保存总结；未完成事项保留，后续安排由用户采用 |

日计划不需要精确到整天的每一分钟。优先说清今天要推进什么、先做哪一步、这一轮预计投入多久。临时工作可以直接开始并记录，之后再决定是否加入计划。

## 三者的分工

| 部分 | 主要职责 |
| --- | --- |
| Hermes 中的 Coach | 用户询问时读取最新事实，拆分候选卡片、讨论卡点、安排日计划或生成总结 |
| Inky Paper | 承接已采用卡片；由用户启动番茄钟；保存进度、反馈和必要调整 |
| Markdown 文档 | 持续保存可读的任务、计划与执行记录；保存用户请求生成的 Coach 总结和个人复盘 |

Coach 能查全部任务和历史；每次用户询问时先读今天与相关任务，需要时追溯更早的记录。Paper 中改过的安排应能在下一次 Coach 对话中读到，不能只依赖聊天里记住的旧内容。执行数据回流是更新共同可读的记录，保存记录本身不唤醒 Agent。

## 卡片怎样选择和执行

建议一张卡片代表一个有明确结果、可以开始的步骤，关联它所属的待办任务。它可以跨多轮完成；建议时长只用于开始第一轮，不承诺整件事一定在该时长内完成。

卡片优先展示动作名称、所属任务、预期结果和首轮建议时长；依赖、拆分理由等信息按需展开。例如，用户询问“帮我拆一下项目周报”，Coach 可以给出以下候选。示例中的方框用于说明交互，正式功能需要可点击的卡片选择控件。

| 选择 | 卡片 | 所属任务 | 预期结果 | 首轮建议 |
| --- | --- | --- | --- | --- |
| ☑ | 列出本周三个关键结论 | 项目周报 | 三条结论及对应证据线索 | 25 分钟 |
| ☑ | 补齐结论需要的数据 | 项目周报 | 关键数字及其来源 | 25 分钟 |
| ☐ | 整理成可发送的周报 | 项目周报 | 一版完整初稿 | 25 分钟 |

用户可修改内容、调整顺序，再点击“将所选卡片加入 Inky”。选择表示采用计划，不表示工作完成；未选卡片留在候选中。若选中卡片依赖未选事项，说明依赖并允许用户调整，不悄悄加入未选项。

卡片保留两个独立状态：采用状态为“候选／待保存／已加入”，执行状态为“待开始／进行中／已完成”。暂停、部分进展和卡点写在执行记录中，未完成卡片可以继续；移出今日计划不等于删除所属任务或历史。

已加入的卡片显示其最新执行状态，并可再次安排到其他日期或调整后续动作，沿用原任务与步骤关联。不能把同一卡片每次重试或跨天安排都创建为一个新任务。

## 计划、步骤和番茄钟怎样对应

一个任务可以持续多天；每天只安排其中想推进的部分。一个步骤可以用多轮完成，一轮结束也可能只产生部分进展。

例如“完成项目周报”是任务，“列出三个结论”是步骤，“先做 25 分钟”是这一轮的安排。结束计时、完成步骤和完成整个任务分别记录，由实际反馈决定状态。

当天临时调整计划时保留已经做过的记录。任务后来改名、重排步骤或更换下一步，也不能改写已经开始那一轮的任务与动作快照。

## Markdown 打开后应该看到什么

文档位于 Paper 数据目录的 `工作记录` 文件夹：`任务.md` 汇总全部任务；`每日/YYYY-MM-DD.md` 保存每日计划、执行记录和按需生成的总结。`个人笔记.md` 与 `每日/YYYY-MM-DD.个人笔记.md` 由用户编辑，自动同步不会覆盖。

以下是展示内容的虚构样例，不是使用者的真实记录：

```markdown
# 2026-09-13

## 今日计划
- 项目周报：完成大纲，再整理关键数据。
- 学习：读完本章，留下一段自己的解释。

## 实际记录
| 时间 | 任务与动作 | 计时 | 结果 |
| --- | --- | --- | --- |
| 09:00–09:25 | 周报 · 列出三个结论 | 25 分钟 | 已完成大纲，周报仍在进行 |
| 09:35–09:55 | 周报 · 整理关键数据 | 20 分钟 | 缺少一个数据来源，暂时停下 |

## 每日工作总结
由 Coach 应用户请求生成，截至 10:00 的记录。
- 已完成周报大纲，关键数据整理尚未完成。
- 记录到两轮工作，累计计时 45 分钟。
- 当前卡点：缺少一个数据来源。
- 下一步建议，尚未采用：先确认缺失数据的来源，再继续整理。

## 个人复盘
先写结论比较容易开始。
```

开始、结束、暂停和已选择的反馈由 Paper 自动写入；产出与卡点允许留空。没有请求 Coach 总结的日期，仍然有完整的计划和实际记录。个人复盘由使用者填写，Coach 的解释和建议有明确标记，不能混成已发生的事实或替使用者改写复盘。

用户已确认保留 SQLite 维护任务和计时的一致性，自动生成可读 Markdown，个人笔记可编辑。任务和计时在 Paper 或专用接口中修改；生成区的手改不会导入任务，重写前另存手改备份。Coach 读取每日记录时同时读取个人笔记，并校验笔记与记录版本。

## 各部分怎样同步

计划和执行事实由统一的数据入口读写，Coach 与 Paper 不分别维护两套可独立覆盖的任务。任务、步骤、每日计划项和执行轮次有稳定关联；候选卡片采用后关联到正式步骤，Markdown 保留这些关联所需的信息，普通阅读时不需要理解技术标识。

| 数据发生在哪里 | 何时同步什么 | 对用户意味着什么 |
| --- | --- | --- |
| Coach 给出候选卡片 | 用户选择之前保留为候选；选择后提交卡片的确定内容、所属任务及计划日期 | 未采用的建议不混入正式计划 |
| 用户点击“加入 Inky” | 统一保存所选计划并返回保存结果；Paper 读取对应记录 | 一次选择后不必在另一端重复采用；只有实际保存成功才显示“已加入” |
| 用户在 Paper 调整或执行 | 更新同一任务／步骤的进度，追加对应轮次、产出和卡点，保存为可读记录 | 无需回 Hermes 手动汇报；既往执行快照保留 |
| 用户再次询问 Coach | 读取最新任务、计划与执行记录，再回答或提出新的候选 | 原有对话也能接上在 Paper 做过的工作 |
| 用户请求每日总结 | 汇总指定日期的计划、实际执行和反馈，记录数据截至时间，保存总结 | 总结与当日事实对应，建议保留为建议，不直接更改计划 |

保存中的安排显示“正在保存”；失败时保留选择和草稿，显示“待保存，可重试”。同一次提交的重试不重复创建任务、计划项或记录。一次提交的多张卡片按一批保存，任何一项发生冲突都不能把整个批次显示为已保存。

提交旧卡片前校验对应任务和步骤是否已变化。已变化时展示差异，保留用户选择，核对后再更新；不能用旧对话内容静默覆盖 Paper 中的新进度。新的计划只影响后续轮次，正在计时的动作保留开始时的内容。

Paper 尚未连接时可以继续讨论候选；无法确认保存就保持“待保存”。重连后先核对原提交是否成功，再补交缺失的保存。Coach 无法读取最新记录时说明信息截至何时，不宣称已同步或给出覆盖全天的最新总结。首版由用户打开 Paper，不自动启动退出的应用。

## 每日工作总结怎样生成

只有用户明确询问总结或复盘时才调用 Coach。回答依据指定日期已经保存的记录，建议采用“实际推进、计划差异、卡点、下一次起点”四部分。总结覆盖计划内和临时进行的工作，不遗漏未加入今日计划但确实发生的轮次；计时总量只是记录，不能表述为有效专注时长。

跨天任务每天总结当天发生的推进，完成步骤与完成父任务分别计算。跨午夜的轮次要保留起止日期；若展示按日计时，按实际计时区间分配，不能把同一段时间在两天重复计算。未记录的产出保持未报告，不根据卡片标题编造成果。

每次总结关联所读记录的版本或截至时间。生成期间若相关记录改变，保存前重读核对；保存后又有新工作，原总结保留其截至时间并标记有新记录。再次生成只在用户请求时发生，新总结不能覆盖个人复盘。总结中提到的明日安排仍是建议，用户选择后才成为正式计划。

## Coach 怎样提供有用的帮助

用户主动询问时，首版建议围绕四类具体问题展开：

| 情况 | Coach 应提供的帮助 |
| --- | --- |
| 事情太多，不知道先做什么 | 结合期限、依赖、用户重视的目标和可用时间，给出今天的顺序及理由 |
| 知道要做什么，但难以开始 | 缩小到一个可以立刻执行、能看出结果的动作 |
| 做了一轮，卡住或进展有限 | 先区分缺信息、动作过大、依赖未满足或用户报告的疲劳，再建议对应调整 |
| 想知道怎样安排得更合适 | 对照计划、产出和用户反馈，提出一个可以在后续工作中检验的小调整 |

建议用具体记录作依据，并区分事实与推测。例如：“上一轮记录了缺数据；建议下一轮先找到来源。若数据已补齐，就直接继续整理。”缺少反馈时保留未知，不能仅根据计时或窗口变化给专注力、精力和生产力打分。

专业知识需要落到使用情境和可解释的方法。作为初始参考，“如果遇到某种情况，就采取某个动作”的执行意图方法，可用于设计起步和卡点后的应对；依据见 [Gollwitzer 与 Sheeran 的研究综述](https://www.sciencedirect.com/science/article/abs/pii/S0065260106380021)。这是产品设计中的应用建议，并不保证对每个人都有效。

休息建议也要保留证据边界：一项微休息元分析发现，对活力和疲劳有小幅改善，整体绩效提升并不显著，不能据此宣称固定的番茄钟时长是最佳方案。[Albulescu 等，2022](https://journals.plos.org/plosone/article?id=10.1371/journal.pone.0272460)

用户已确认新增专用 Hermes 插件。`inky-coach:coach` 提供按需角色和工作方法，Paper MCP 提供读取、候选和总结接口；对话中的卡片控件负责选择、编辑、排序和采用。定时刷新只读取状态，不调用模型。

## 后续验证什么

| 场景 | 必须观察到的行为 |
| --- | --- |
| 三张卡片选两张后保存，并重复提交一次 | Paper 只出现选中的两项，没有重复任务或自动计时 |
| 在 Paper 完成一张卡片，另一张记录卡点，然后询问 Coach | Coach 读到最新进度，保留父任务状态，正确区分完成与卡住 |
| Paper 调整过步骤后，尝试采用旧对话中的卡片 | 显示冲突并保留草稿，既往轮次内容和新进度不被覆盖 |
| 断连后重试保存，随后请求每日总结 | 保存状态可核实，记录不重不漏，总结的数据截至时间明确 |
| 结束番茄钟、长时间未操作或有新记录，但用户没有询问 | 照常记录与同步，不调用 Coach、不生成建议或总结 |

实际试用还要检查是否减少重复输入，以及当日 Markdown 能否帮助使用者看清进展。实现和运行验证结果记录在 `2026-09-13-implementation-steps.md`，不将功能验收当作长期使用效果的证据。
